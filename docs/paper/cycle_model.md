Generated by `software/analysis/cycle_model.py`. Part 1 checks the model against simulation and the board; Parts 2 and 3 are **predictions** (model, not measured).

## Part 2 - prediction: whole-frame line-buffer pipeline, all layers at once

Assumptions: no tiles (no halo recomputation); each layer streams with a fixed cycles-per-pixel; lanes = whole output channels x whole kernel steps; requantizers = ceil(C_out / cycles-per-pixel), 2 DSP each; 32-bit output stream (4 bytes/cycle); fill = (K-1) rows per layer; no stalls; ARM padding 5.9 ms added (as measured today). Real designs lose some of this to stalls and control.

Two I/O cases: today's byte-wide load/output (72,052 cycles per tile, not overlapped) and fully overlapped I/O (0). ARM/DMA overhead as measured today (61.5 ms per frame) is added. ## Part 4 - prediction: the r0_125 build (deployed network, one more register per engine run, fabric clock 125 MHz)

Same architecture as today plus one register between the activation RAM mux and the MAC DSP (`docs/paper/fmax_plan.md`). The build exists (branch `r0_125`, routed WNS +0.632 ns at 125 MHz, 0 failing endpoints) and is simulated, but it has NOT run on the board: the frame times below are model predictions. Cycles per tile = board mean 926,220 + 4; ARM/DMA overhead held at 61.5 ms (as in Part 3).

| Clock | Cycles per tile | Core time per frame | Frame time (predicted) | fps (predicted) |
|---|---|---|---|---|
| 100 MHz | 926,224 | 1,250.4 ms | 1,311.9 ms | 0.762 |
| 125 MHz | 926,224 | 1,000.3 ms | 1,061.8 ms | 0.942 |

Caveats: the 125 MHz build met timing in Vivado (post-route, not on the board); 150 MHz is NOT shown to close timing. Today's whole system has WNS +0.503 ns at 100 MHz, and a 152.38 MHz trial of the unchanged design failed by 1.693 ns (`docs/paper/timing_150mhz.md`; path: activation RAM -> split-RAM mux -> MAC DSP input), so the 150 MHz figures of Part 3 still need a pipelining change. Do not mix the two 3.9 fps figures: Part 2's is the line-buffer pipeline at 100 MHz, Part 3's is the shared engine at 150 MHz with fully overlapped I/O. The 32-bit stream caps the pipeline at 3 cycles per LR pixel (64-bit would halve that); DSP packing of two INT8 multiplies is not modelled.

## Part 5 - prediction: next architecture, (i) one shared engine with all DSPs vs (ii) a line-buffer layer pipeline

Both with the R3q network (same layers; the anchor add sits in the last requantizer, no extra cycle). Model, NOT measured.

(i) Shared engine: today's tiles (64x64 + 3 px halo, halo recomputed), layers one after another, every layer gets all lanes (`shared_engine()`, Part 3 method). Frame time = 135 tiles x (engine + I/O cycles) / clock + today's ARM/DMA overhead (61.5 ms: the ARM still cuts and places tiles).

(ii) Layer pipeline: whole frame streamed in raster order, no tiles, all four layers at the same time, 2-row line buffers for the 3x3 layers (`best_pipeline()`, Part 2 method). Frame time = slowest stage + fill (2 rows per 3x3 layer) / clock + ARM padding 5.9 ms (no tile copy: the DMA reads the padded frame and writes the 1920x1080 output in place).

| Design | DSP | Lanes L1/L2/L3/L4 | Cycles/px per layer | Cycles per frame | 100 MHz | 125 MHz |
|---|---|---|---|---|---|---|
| (i) shared, I/O as today | 208 | 144/144/128/192 | 3/2/2/9 | 18.93 M | 251 ms / 4.0 fps | 213 ms / 4.7 fps |
| (i) shared, I/O overlapped | 208 | 144/144/128/192 | 3/2/2/9 | 9.20 M | 154 ms / 6.5 fps | 135 ms / 7.4 fps |
| (ii) layer pipeline | 168 | 27/9/16/108 | 16/16/16/16 | 8.48 M | 91 ms / 11.0 fps | 74 ms / 13.6 fps |

(i) is given the whole device (220 DSP) and picks its own number of requantizers (it uses 208). (ii) uses 168 DSP: 16 cycles per output pixel in EVERY layer (rate-matched), which more DSPs cannot shorten without breaking that balance (best_pipeline at 200-220 DSP gives 8.29 M stage cycles, 1.1% fewer, for 34 more DSPs and uneven layers).

## Part 6 - prediction: pipeline v2, more MAC lanes (DSP + LUT multipliers)

Why: the built pipeline is multiplier-bound. 160 lanes x 16 cycles per pixel = 2,560 = the MACs per pixel, so its lanes are 100 % busy while computing; the measured 8,398,481 cycles per frame are 16.2 cycles per LR pixel. A faster frame needs more lanes (or a faster clock). Model, NOT measured; nothing below is built.

Method: same four stages and the same network (R3q weights, anchor in the last requantizer). For a target cycles-per-pixel each layer gets the smallest clean lane count that reaches it (`lane_options`), requantizers = ceil(C_out / cycles), 2 DSP each. Lanes go to DSPs first (220 - requantizers - 2 other), the rest are LUT multipliers. Frame cycles from `pipeline_frame_cycles` x calibration 0.9900 (built pipeline: model 8,483,392 vs simulated 8,398,481). Frame time = cycles / clock + measured overhead: cached 28.2 ms (pad + cache maintenance, depends on image size only) or non-cacheable buffers 3.3 ms (pad only).

Resources scale from the routed pipeline: 36.6 LUT / 68.5 FF per lane, +96 LUT / +50 FF per LUT multiplier (`dsp_vs_lut.md`), plus the measured fixed part (4,032 LUT). Block RAM stays ~25 tiles (line buffers do not grow with lanes).

Row 16 is the built design. It reproduces the routed numbers (DSP 170 vs 170, LUT 9,888 vs 9,888, 125 MHz 95.36 vs board 95.36 ms) BY CONSTRUCTION, because the per-lane costs, the cycle calibration and the overheads are taken from it. It is not an independent check; the other rows are extrapolations.

Reading:

* **12 cycles/px = low-risk step**: only 20 LUT multipliers, 27 % LUT; 18.6 fps at 125 MHz with non-cacheable buffers.
* **8 cycles/px = the sweet spot**: 2x the lanes (118 as LUT multipliers), about half the LUTs; 36.9 ms = 27 fps at 125 MHz with non-cacheable buffers, 22 fps at 100 MHz. With cached buffers the measured 28.2 ms of padding + cache maintenance stays, so 16 fps: the buffer choice matters as much as the RTL. 30 fps needs 8 cycles/px plus about 140 MHz, or 6 cycles/px.
* 6 cycles/px reaches 35 fps on paper but needs 84 % of the LUTs; 4 and 3 cycles/px do not fit (over 100 %). Routing and timing at 125 MHz are the main risk above 8 cycles/px (the built pipeline closes 125 MHz with only +0.267 ns slack at 19 % LUT use; one LUT-multiplier engine closed 133 MHz alone, out of context). LUT per lane is assumed constant; wider adder trees (L4: 216 or 288 lanes) may cost more.
* 3 cycles/px is the 32-bit output stream limit (12 bytes per LR pixel); going below it needs a 64-bit stream (not modelled).

Not modelled: AXI/DDR stalls (the built design shows none: DMA wait = core cycles), placement/routing congestion, DSP packing of two INT8 multiplies (on the DSP48E1 the 25x18 multiplier leaves no guard bits for two accumulated int8 x uint8 products, so it is not counted), power. A 100 MHz build is the safe fallback if 125 MHz does not close.
